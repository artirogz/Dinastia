# Роутер задачи: размер → процесс, риск → проверки

Две независимые оси. Размер выбирает, сколько церемонии до кода. Риск выбирает, какие проверки
обязательны после. **Риск никогда не снижается размером:** пять строк в обработчике оплаты — это
T0 по размеру и R2 по проверкам.

## Ось 1: размер

| Трек | Признаки | Процесс |
|---|---|---|
| **T0** | ≤ 1 файл, ≤ ~20 строк, требование однозначно | сразу правка → `npm run typecheck && npm test` на затронутом |
| **T1** | ≤ 3 файлов, требования ясны | мини-план в чате (цель, подход, файлы, тесты, риски: 3–5 строк) → вопросы батчем, если уверенность < 95 % → реализация, тест до фикса, если чинится баг → самопроверка диффа → проверки |
| **T2** | несколько подсистем, или требования мутные, или больше дня работы | короткая спека в `docs/specs/<дата>-<тема>.md` (что, зачем, границы, критерий готовности, таблицы/ручки) → **критика спеки свежей сессией на Opus** (5 вопросов ниже) → план из 2–4 крупных задач → реализация → одно ревью всей ветки → проверки |

Этап дорожной карты (M1…M8) — всегда T2: у него есть документ в `docs/`, он и есть спека, критикуется
он.

**Пять вопросов критику спеки:** (1) у каждой задачи есть проверяемый признак закрытия (команда,
скриншот, замер), а не «сделать хорошо»? (2) какие допущения приняты без проверки («хостинг умеет»,
«вебхук придёт»)? (3) противоречия с `docs/01-architecture.md` и `PROJECT-STATE.md`? (4) что
забыто: соседние ручки, симметричные ветки, удаление и откат? (5) не хранится ли производное
(счётчик, который можно вычислить; маскированный или склеенный текст вместо данных)?

## Ось 2: риск

| Уровень | Признаки | Обязательные проверки на выходе |
|---|---|---|
| **R0** | внутренний код, пользователь не увидит | typecheck + тесты |
| **R1** | экран, текст бота, поведение, которое увидит ученик или владелец | + `visual-fidelity-loop` для экранов (скриншот в контексте, сравнение с макетом) + `verification-rubrics` («владелец примет?») |
| **R2** | деньги, вход и сессии, права доступа, вебхуки, миграции и необратимые изменения данных, персональные данные, рассылки | + ревью **свежей сессией на Opus** с мандатом «найди способ сломать»: чужая сессия, доступ без покупки, двойная выдача, потеря оплаты, утечка ПД. Каждая находка — с воспроизводящим запросом. Чинить → второй круг. Без этого этап не закрыт |

Уровни складываются: экран оплаты = R1 + R2.

## Объяви маршрут

До первой правки одной строкой в чате:

```
[dev-flow] T1 × R2 → проверки: typecheck, тесты, ревью свежей сессией
```

Скоуп вырос по ходу (файлов больше, «а ещё надо…») → перейди на трек выше с текущего места и
повтори строку. Понижать трек на лету нельзя.

## Инварианты всех треков

- **Проверка перед «готово».** Прогнать команду, прочитать вывод, только потом сообщать результат.
  «Должно работать» не говорится.
- **Документация библиотеки до кода.** Перед кодом против Next.js, Drizzle, grammY, pg-boss, SDK
  Telegram, API ЮKassa или Kinescope — сверка с актуальной документацией (context7 или официальный
  сайт). Память о сигнатурах устаревает.
- **Фикс класса, а не экземпляра.** Починил баг → `grep -ri` по признаку, перечисли все похожие
  места, у каждого: починено или почему нет. Класс выразим тестом → тест-сканер исходников.
- **Тест на баг пишется до фикса** и должен быть красным.
- **Чистый вывод подозрителен.** Ноль ошибок на первой попытке — проверь, что проверка вообще
  смотрела на нужный слой.

## Красные флаги

| Мысль | Реальность |
|---|---|
| «Это просто, пропущу проверку» | проверка обязательна на всех треках |
| «Всего пять строк, хоть и в оплате» | риск бьёт размер: R2 |
| «Начал по-лёгкому, доделаю по-лёгкому» | скоуп вырос → эскалация сейчас |
| «Прогоню полный цикл на всякий случай» | церемония на T0 — тоже ошибка маршрута: токены и время |
| «Знаю этот API, напишу по памяти» | сверка с документацией до кода |
| «Спека написана, кодим» | T2 без критики спеки = маршрут не пройден |
