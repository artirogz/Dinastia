# 06 — Бот, прогревы, рассылки

Бот — вход для всех, приложение — для купивших. Перед кодом против grammY, pg-boss и Bot API Claude
сверяется с актуальной документацией (методы и опции ниже названы по памяти и помечены, где важно).

## 1. Структура кода

```
src/bot/index.ts          createBot(): собирает grammY Bot, подключает модули ниже
src/bot/start.ts          /start, deep-link, согласие
src/bot/menu.ts           главное меню, «Мои курсы», «Купить», «Помощь»
src/bot/buy.ts            сцена покупки: курс → контакт для чека → createPayment()
src/bot/admin.ts          админ-команды (guard по users.role = 'admin')
src/lib/telegram/send.ts  единственный исходящий канал вне ответов на апдейт
src/lib/funnels/          парсинг yaml, планирование шагов, стоп-условия
src/worker/jobs/          funnel-step.ts, broadcast.ts, payments-reconcile.ts, payments-review.ts, cleanup.ts
src/app/api/tg/webhook/route.ts   webhookCallback(bot, "std/http", { secretToken })
```

Вебхук-роут проверяет заголовок `X-Telegram-Bot-Api-Secret-Token` (`TG_WEBHOOK_SECRET`) и отвечает
401 без тела, если он не совпал. Бот инициализируется один раз на процесс (`bot.init()`), чтобы
не ходить в `getMe` на каждый апдейт. `worker` импортирует тот же `createBot()` только ради
`bot.api`, апдейты он не принимает.

## 2. /start и deep-link

Параметр после `/start` бывает трёх видов. Допустимые символы в параметре Telegram: латиница, цифры,
`_` и `-`, до 64 символов, поэтому slug курса и цепочки ограничены регуляркой `^[a-z0-9-]{1,40}$`
(проверяет импорт контента).

| Параметр | Что делает |
|---|---|
| `warmup-<slug>` | записывает пользователя в цепочку `<slug>` (после согласия) |
| `course-<slug>` | показывает карточку курса с кнопкой «Купить» |
| `paid_<orderId>` | возврат с оплаты: показывает статус заказа и кнопку «Открыть приложение»; если заказ ещё `pending`, проверяет его в ЮKassa (`04-payments-yookassa.md` §4) |
| пусто | главное меню |

Порядок обработки `/start`:

1. Upsert `users` по `from.id` (имя, username, язык). Сбросить `bot_blocked_at`, если был установлен.
2. Нет `consent_at` → показать текст согласия, ссылки на политику обработки данных и оферту
   (`POLICY_URL`, `OFFER_URL`) и кнопку «Принимаю». Ничего другого, в том числе запись в цепочку,
   до согласия не происходит. Исходный параметр кладётся в `callback_data` кнопки
   (`consent:<payload>`, укладывается в лимит 64 байта).
3. Нажатие «Принимаю» → `users.consent_at = now()`, `consent_version = CONSENT_VERSION`, затем
   обработка отложенного параметра как в таблице выше. Это согласие на обработку данных и ознакомление
   с офертой; рекламные сообщения оно не разрешает.
4. Следом вторая кнопка «Получать анонсы» (можно пропустить) → `users.marketing_consent_at = now()`.
   Без неё человек получает только служебные сообщения (ответы на команды, чек, «доступ открыт») и шаги
   цепочки, в которую сам вошёл по deep-link; рассылки (§8) идут только тем, у кого есть это поле и нет
   `marketing_opt_out_at`. Тексты обоих согласий и оферты даёт владелец (Q11).
4. Есть согласие → сразу обработка параметра.

## 3. Главное меню

Inline-клавиатура под приветствием:

| Кнопка | Действие |
|---|---|
| Мои курсы | список курсов с активным `entitlement` и кнопкой «Открыть» у каждого (ведёт в приложение на страницу курса) |
| Купить | список опубликованных курсов без доступа, выбор → сцена покупки |
| Открыть приложение | `web_app`-кнопка с `PUBLIC_APP_URL` |
| Помощь | текст с контактом поддержки и ссылкой на политику |

Дополнительно кнопка меню чата (`setChatMenuButton` с типом `web_app`) ведёт в то же приложение
(проверить по Bot API актуальное имя и параметры метода).

`/web` присылает ссылку входа для браузера: создаётся запись в `magic_links` (токен 32 байта,
хранится sha256, срок 10 минут), пользователю уходит `https://app.<домен>/login?token=…`
(`03-auth-and-security.md` §3). Без согласия `/web` не отвечает ссылкой.

`/stop` останавливает все активные прогревы пользователя (`stop_reason='user_stop'`) и ставит
`users.marketing_opt_out_at = now()`: рассылки его больше не включают. Упоминается в приветственном
сообщении каждой цепочки и в каждой рассылке. Снять отказ можно только самому: `/start` → «Получать анонсы».

## 4. Админ-команды

Админ определяется строкой `users.role='admin'`, которая выставляется при старте из `ADMIN_TG_IDS`.
Команды видны в меню Telegram только админским чатам (`setMyCommands` с `scope: chat`). Каждая
команда пишет строку в `admin_actions`.

| Команда | Что делает |
|---|---|
| `/grant <tg_id> <course>` | `entitlement` с `source='manual'`, `granted_by` = админ; срок по `access_days` курса |
| `/revoke <tg_id> <course>` | `ends_at = now()` у действующих выдач, предложение отметить возврат в заказе |
| `/funnel start <slug> <tg_id>` | записывает пользователя в цепочку; отказ, если нет согласия или бот заблокирован |
| `/broadcast <slug>` | загружает `content/broadcasts/<slug>.yaml`, показывает текст и размер аудитории, запуск только по кнопке «Отправить N получателям» |
| `/stats` | число пользователей, согласий, покупок, выручка, активные цепочки, по курсам; без персональных данных |
| `/orders <tg_id>` | последние заказы пользователя: статус у нас и у ЮKassa (перечитывается по API), кнопка «Проверить оплату сейчас» = внеочередной прогон сверки по этому заказу (`04` §4) |
| `/find <email или телефон>` | пользователь по контакту чека (`orders.receipt_contact`), для случая «сменил аккаунт Telegram»; ответ только `tg_id` и курсы, запрос пишется в `admin_actions` |
| `/forget <tg_id>` | удаление по запросу субъекта, алгоритм `03-auth-and-security.md` §8 |

Каждая команда — тонкая обёртка над функцией в `src/lib/admin/*`. Те же функции зовёт `scripts/admin.ts`
(`node dist/scripts/admin.js orders|find|grant|revoke|magic-link|forget …` на сервере): запасной путь на случай,
когда Telegram или бот недоступны. Сценарии для владельца — `docs/12-operations.md`.
| `/forget <tg_id>` | запрос подтверждения, затем обезличивание (`02-data-model.md` инвариант 9) |

Команды принимают `tg_id` как аргумент админа: это единственное место, где `tg_id` приходит не из
подписи, и поэтому проверка роли стоит до разбора аргументов.

## 5. Формат цепочки

`content/funnels/<slug>.yaml`, импортируется в `funnels` и `funnel_steps`:

```yaml
slug: example-warmup
title: Прогрев «Пример»
course: example-course        # курс, который продаёт цепочка; покупка этого курса её останавливает
steps:
  - id: welcome
    delay: 0                  # from enrollment for the first step, from previous step afterwards
    text: |
      Привет, {first_name}! Это первое сообщение цепочки.
      Остановить рассылку: /stop
    media: { type: photo, file: media/welcome.jpg }   # optional, path relative to the yaml
    buttons:
      - { text: "Подробнее о курсе", url: "https://example.com/course" }
  - id: day-2
    delay: 1d
    text: "Второе сообщение через сутки."
    buttons:
      - { text: "Купить курс", action: buy, course: example-course }
```

Поля шага:

- `delay`: `0`, либо число с единицей `m`, `h`, `d`, либо составное (`1d12h`). Считается от записи
  в цепочку для первого шага и от отправки предыдущего для остальных.
- `text`: HTML в подмножестве Telegram (`<b>`, `<i>`, `<a>`), переменные `{first_name}`.
  Подставляемые значения экранируются.
- `media`: `photo`, `video` или `document`; файл копируется в `MEDIA_ROOT` под неизменяемым ключом
  `funnels/<slug>/<hash16>-<file>` (контракт `file_key`, `02-data-model.md` §6), при отправке
  берётся `file_id`, если он уже закеширован, иначе файл загружается один раз.
- `buttons`: `url` (внешняя ссылка), `action: buy` (+ `course`), `action: open_app`, `action: stop`.

Стоп-условия проверяются перед каждой отправкой, а не только в момент события:

1. Есть действующий `entitlement` на `course` цепочки. Дополнительно `handleOrderPaid()` сразу
   останавливает такие записи со `stop_reason='purchased'`.
2. `users.bot_blocked_at` не null → `stop_reason='bot_blocked'`.
3. Пользователь нажал `/stop` или кнопку `action: stop` → `user_stop`.
4. Админ остановил вручную → `manual`. Пользователь обезличен → `forgotten`.

Цепочка выбирается один раз на пару `(funnel, user)`: повторный `/start warmup-<slug>` не запускает её
заново; админ может перезапустить командой `/funnel start`.

## 6. Фоновые задачи (worker, pg-boss)

| Очередь | Запуск | Что делает |
|---|---|---|
| `funnel-step` | `send` с `startAfter` на момент шага, `singletonKey = enrollment:<id>:<step>` | проверить стоп-условия → отправить шаг через `send.ts` → записать `current_step`, `next_run_at` → поставить следующий. Одинаковый ключ не даёт поставить шаг дважды |
| `broadcast` | по кнопке админа | брать пачки `broadcast_recipients` со статусом `pending` и `retry_after` в прошлом, слать через `send.ts`, писать `sent`/`blocked`/`failed` |
| `payments-reconcile` | cron `*/5 * * * *` | сверка платежей по очереди `next_check_at`, `04-payments-yookassa.md` §4 |
| `payments-review` | cron раз в сутки | заказы `pending` старше 7 дней списком администраторам в бот, `04` §4 п. 5 |
| `cleanup` | cron раз в час | удалить `init_data_uses` старше суток и просроченные `magic_links`; удалить файлы под `MEDIA_ROOT`, на которые не осталось ни одной строки (`02` §6, контракт `file_key`) |

Пулы соединений: Drizzle (`postgres.js`) — `max: 5` в `web` и `max: 3` в `worker`; pg-boss держит свой
пул `pg` с `max: 3`. Итого не больше 16 соединений при `max_connections = 100` у Postgres; значения
в одном месте — `src/db/client.ts` и `src/worker/index.ts`, читаются из `DB_POOL_MAX`.

После рестарта `worker` не теряет цепочки: состояние в `funnel_enrollments` и в таблицах pg-boss, и
отдельная задача раз в минуту ставит шаги, у которых `next_run_at` в прошлом, а job не существует.
Версия pg-boss определяет детали API (создание очередей, расписание, опции `send`): сверить с
документацией установленной версии.

Два пула соединений. pg-boss держит свой пул (`pg`), Drizzle работает через `postgres.js`, поэтому
постановка задачи не входит в транзакцию Drizzle. Порядок всегда один: сначала коммит транзакции, потом
`boss.send` с `singletonKey`. Задача при старте перепроверяет состояние в базе (цепочка не остановлена,
заказ не отменён, шаг не отправлен) и при расхождении выходит без отправки.

## 7. Лимиты Telegram и единственный модуль отправки

Ориентиры Bot API (подтвердить по документации Telegram, раздел про лимиты рассылок):

- около 30 сообщений в секунду на всего бота; в проекте потолок 25 в секунду с запасом;
- не чаще одного сообщения в секунду в один чат;
- ответ 429 содержит `parameters.retry_after` в секундах: пауза обязательна;
- ответ 403 («bot was blocked by the user» и родственные) означает, что писать этому человеку
  больше нельзя.

`src/lib/telegram/send.ts` — единственная точка исходящих сообщений вне ответа на входящий апдейт
(прогревы, рассылки, «доступ открыт», карточки жалоб админу):

1. Ограничитель скорости: общий бакет 25/с и отдельный интервал 1/с на `chat_id`. Состояние в
   памяти процесса; `worker` — единственный процесс, который слает пачками.
2. 429 → вся очередь отправителя стоит `retry_after` секунд плюс небольшой случайный добавок,
   получатель получает `retry_after` в `broadcast_recipients`, попытка не считается ошибкой.
3. 403 → `users.bot_blocked_at = now()`, активные цепочки пользователя останавливаются
   (`bot_blocked`), получатель рассылки получает `blocked`.
4. Прочие 4xx (чат не найден, пользователь удалён) → `failed` с текстом ошибки, без повторов.
5. 5xx и сетевые ошибки → до трёх повторов с нарастающей паузой, затем `failed`.
6. Тексты сообщений в логи не пишутся: только внутренний `user_id`, тип сообщения и результат.

Ответ на действие пользователя через `ctx.reply` допустим: это одно сообщение в чат, из которого
пришёл апдейт. Все остальные места, где встречается `bot.api.send*` или `api.send*`, обязаны
идти через модуль. Это проверяет тест-сканер `tests/send-invariant.test.ts`: он перечисляет
исходники и падает, если такой вызов появился вне `src/lib/telegram/send.ts`.

## 8. Формат рассылки

`content/broadcasts/<slug>.yaml`: те же поля `text`, `media`, `buttons`, что у шага цепочки, плюс
аудитория.

```yaml
slug: launch-announce
text: "Новый курс открыт."
buttons:
  - { text: "Посмотреть", action: buy, course: example-course }
audience:
  warmup: example-warmup      # optional: enrolled in this funnel
  purchased: false            # optional: has no active entitlement to `course`
  course: example-course
```

Всегда исключаются: пользователи без `consent_at`, без `marketing_consent_at`, с `marketing_opt_out_at`,
с `bot_blocked_at`, обезличенные. Фильтр стоит в одном месте — в выборке аудитории воркера, и проверяется
ещё раз перед каждой отправкой (человек мог нажать `/stop` после предпросмотра). Сначала админ
видит предпросмотр и размер аудитории, потом нажимает «Отправить». Автоматического запуска
рассылок после деплоя или импорта нет.
