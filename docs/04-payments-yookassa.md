# 04 — Оплата через ЮKassa

Поверхность класса «деньги»: любая правка в этом разделе проходит отдельное ревью (`dev-flow-lite`,
уровень R2). Перед кодом против API ЮKassa Claude сверяется с актуальной документацией
(https://yookassa.ru/developers): поля запроса, коды ошибок и список IP ниже даны как ориентир и
помечены «уточнить по документации» там, где мы их не подтверждали.

## 1. Схема целиком

```
бот: выбрать курс → контакт для чека → createPayment() → кнопка «Оплатить» (confirmation_url)
                                                          │
пользователь платит на странице ЮKassa → return_url = https://t.me/<bot>?start=paid_<orderId>
                                                          │
ЮKassa ──► POST /api/payments/webhook ──┐                 │
                                        ├─► handleOrderPaid(paymentId, payment) ──► entitlement + бот-сообщение
worker: payments-reconcile, каждые 5 мин ┘
```

Два независимых пути ведут в одну функцию. Вебхук быстрый, сверка страхует от потерянного вебхука.

**Канал продаж — открытый вопрос Q10.** Правила Telegram требуют проводить оплату цифровых товаров и услуг
внутри Telegram только в Stars (https://core.telegram.org/bots/payments-stars). Схема выше выводит оплату
на внешнюю страницу ЮKassa по ссылке из бота; допустимость этого для бота формально не подтверждена, и
решение принимает владелец до начала M4 (`11-decisions.md`, ADR-005, дополнение). Если выбран Stars,
`createPayment()` получает второй адаптер (`sendInvoice` с валютой `XTR`, `payment_id` =
`telegram_payment_charge_id`), а `handleOrderPaid()`, `orders` и `entitlements` не меняются.

## 2. Заказ и платёж в боте

1. Пользователь выбирает курс. Если у него уже есть активный `entitlement` на этот курс, покупка не
   начинается.
2. Бот спрашивает email или телефон для чека 54-ФЗ. Формат проверяется на сервере (простая проверка
   email или телефон в международном формате). Контакт не сохраняется в профиле, только в
   `orders.receipt_contact`.
3. `createPayment()` в одной транзакции создаёт `orders(status='pending')`. Если для пары
   `(user, course)` уже есть `pending`-заказ (partial unique `orders_one_pending_uq`), решение о нём
   принимает статус платежа у ЮKassa, своего срока жизни у заказа нет:
   - `payment_id` заполнен: платёж читается через `GET /v3/payments/{id}`. `succeeded` идёт в
     `handleOrderPaid`, и бот отвечает «доступ уже открыт». `pending` (и `waiting_for_capture`, который
     при `capture: true` не ожидается, но конечным не считается) означает, что платёж ещё можно
     оплатить: заказ переиспользуется, бот присылает тот же `confirmation.confirmation_url`. Только
     `canceled` переводит заказ в `canceled` (`cancelOrder`), после чего создаётся новый заказ.
   - `payment_id` пуст (процесс упал между вставкой заказа и ответом ЮKassa): `createPayment()`
     повторяется для этого же заказа с тем же ключом идемпотентности, пока заказу меньше 24 часов
     (§4, п. 3). Старше 24 часов заказ закрывается локально: ответа с `confirmation_url` мы не получили,
     покупатель кнопку оплаты не видел и оплатить такой платёж не мог.

   Двойное нажатие попадает на тот же `pending`-заказ и не создаёт второй платёж. Ключ
   идемпотентности всегда равен `orders.id`, у нового заказа он новый.

   Гонка «заказ закрыли, а его оплатили» исключена построением: локально `canceled` ставится только
   после того, как ЮKassa сама вернула `canceled`, а этот статус у неё конечный, оплатить такой платёж
   нельзя. Поэтому `handleOrderPaid` переводит в `succeeded` только `pending`, и других путей из
   `canceled` нет.
4. Запрос в API ЮKassa с заголовком `Idempotence-Key: <orders.id>`:

```ts
// POST https://api.yookassa.ru/v3/payments   (Basic auth: shopId:secretKey)
// Verify field names, vat_code values and tax_system_code against current YooKassa docs.
const body = {
  amount: { value: (order.amountMinor / 100).toFixed(2), currency: order.currency },
  capture: true,
  confirmation: {
    type: "redirect",
    return_url: `${process.env.YOOKASSA_RETURN_URL}${order.id}`, // prefix https://t.me/<bot>?start=paid_ (section 8)
  },
  description: `Курс «${course.title}»`.slice(0, 128),
  metadata: { order_id: order.id },
  receipt: {
    customer: contact.includes("@") ? { email: contact } : { phone: contact },
    items: [{
      description: course.title.slice(0, 128),
      quantity: "1.00",
      amount: { value: (order.amountMinor / 100).toFixed(2), currency: order.currency },
      vat_code: Number(process.env.YOOKASSA_VAT_CODE), // depends on the seller's tax regime
      payment_subject: "service",
      payment_mode: "full_payment",
    }],
  },
};
```

5. Ответ: `id` платежа и `confirmation.confirmation_url`. Сервер пишет `orders.payment_id` и
   `raw_payload`, бот присылает кнопку «Оплатить» с этим URL.

Правила:

- `Idempotence-Key` равен `orders.id`. Повтор запроса с тем же ключом в течение 24 часов вернёт тот же
  платёж; позже ЮKassa считает его новым запросом (раздел про формат взаимодействия:
  https://yookassa.ru/developers/using-api/interaction-format, срок уточнить по документации).
- Чек обязателен в каждом платеже, если в кабинете включена фискализация (на старте считаем, что
  включена). Без контакта платёж отбивается с ошибкой про чек. «Спросим email на странице оплаты»
  не работает: контакт нужен до создания платежа.
- `vat_code` и система налогообложения должны совпадать с настройками продавца (ИП на УСН,
  самозанятый и т. д.). Значения для конкретного режима владелец уточняет у бухгалтера; код берёт
  `YOOKASSA_VAT_CODE` из окружения и не зашивает число.
- `capture: true`: деньги списываются сразу, этап подтверждения не нужен.
- Сумма берётся только из `courses.price_minor` и промокода на сервере. Цена из клиента не принимается.

## 3. Вебхук

Роут `POST /api/payments/webhook`. Порядок действий строгий:

1. Определить IP отправителя. За Caddy это первый адрес в `X-Forwarded-For`: Caddy перезаписывает
   этот заголовок для запросов не из доверенных прокси, поэтому клиент подделать его не может
   (проверить `curl`-ом с заголовком `X-Forwarded-For: 1.2.3.4` и убедиться, что в логе приложения
   другой адрес).
2. IP не из диапазонов ЮKassa → 403 без тела. Диапазоны хранятся константой в
   `src/lib/payments/yookassa-ips.ts`; актуальный список — в документации ЮKassa, раздел про
   HTTP-уведомления (уточнить по документации, список обновляется). На момент написания пакета это
   `185.71.76.0/27`, `185.71.77.0/27`, `77.75.153.0/25`, `77.75.154.128/25`, `77.75.156.11`,
   `77.75.156.35` и IPv6 `2a02:5180::/32`.
3. Разобрать тело, взять `event` и `object.id`. События, которые мы обрабатываем:
   `payment.succeeded` и `payment.canceled`. Остальные → 200 и выход.
4. **Телу не верим.** По `object.id` читаем платёж через `GET /v3/payments/{id}` и дальше работаем
   только с ответом API. Статус в ответе `succeeded` → `handleOrderPaid(paymentId, payment)`. `canceled` →
   `cancelOrder(paymentId)`: `UPDATE orders SET status='canceled' WHERE payment_id=$1 AND status='pending'`.
5. Ответить 200 быстро. Повторная доставка при не-200 идёт сколько-то раз с интервалами (уточнить
   по документации), поэтому ошибка нашей стороны должна давать 5xx, а «платёж не наш» — 200.
6. `GET /api/payments/webhook` возвращает 200: ЮKassa может проверять доступность адреса.

**Известная грабля.** HTTP-уведомления подключаются в личном кабинете ЮKassa (Интеграция →
HTTP-уведомления), а не через API ключом магазина: запрос к `/v3/webhooks` с `shopId:secretKey`
отвечает `invalid_credentials` («Authentication type is not allowed»), для него нужен OAuth-токен
партнёра. Поэтому: (а) владелец вносит URL вебхука руками, (б) мы не полагаемся на вебхук одним
каналом, а держим сверку. Признак, что подписки нет: ноль обращений к `/api/payments/webhook` в
логе после тестовой оплаты.

## 4. Сверка (reconcile)

Задача `payments-reconcile` в `worker` на pg-boss, расписание каждые 5 минут. Очередь проверок
хранится в самом заказе: столбец `orders.next_check_at` (`02-data-model.md`, DDL `orders`), при
создании заказа он равен `created_at + 2 минуты` (вебхук обычно успевает раньше).

1. Выбрать заказы `where status = 'pending' and next_check_at <= now() order by next_check_at limit 100`
   (индекс `orders_pending_next_check_idx`). Проверенный заказ уходит в конец очереди, поэтому старые
   заказы не занимают каждый проход и новые не ждут за ними.
2. Для заказа с `payment_id`: `GET /v3/payments/{payment_id}`. `succeeded` → `handleOrderPaid(paymentId, payment)`;
   `canceled` → `cancelOrder()`; `pending` и прочие → только сдвиг `next_check_at` (п. 4).
3. Заказ без `payment_id` (упали между созданием заказа и ответом ЮKassa): моложе 24 часов →
   повторить `createPayment()` для этого заказа с тем же ключом идемпотентности, ЮKassa вернёт тот же
   платёж, если он был создан, или создаст новый; старше 24 часов → `status = 'canceled'` локально
   (почему это безопасно, §2, п. 3).
4. Шаг следующей проверки растёт с возрастом заказа: моложе часа `now() + 5 минут`, моложе суток
   `now() + 1 час`, дальше `now() + 6 часов`. Сверка не бросает заказ ни в каком возрасте: пока
   ЮKassa не вернула конечный статус, заказ проверяется раз в 6 часов. Цена шага: без вебхука оплата,
   сделанная через час после создания заказа, подтянется сверкой в пределах часа; покупатель, вернувшийся
   в бот по `paid_<orderId>`, получает точечную проверку сразу (ниже).
5. Заказы `pending` старше 7 дней требуют разбора человеком: ЮKassa отменяет неоплаченные платежи
   намного раньше (срок уточнить по документации), и такой заказ означает расхождение. Отдельная
   задача `payments-review` раз в сутки присылает администраторам (`ADMIN_TG_IDS`) список таких заказов:
   id, пользователь, сумма, `payment_id`, статус платежа у ЮKassa. Статус заказа при этом не меняется:
   `pending` держит место в `orders_one_pending_uq` и остаётся доступным для `handleOrderPaid`, если
   платёж всё же пройдёт. Пустой список ничего не присылает.
6. Запросы к API с паузой 200 мс и таймаутом; ошибка одного заказа не останавливает остальные, его
   `next_check_at` сдвигается по п. 4.
7. В лог одна строка за запуск: сколько проверено, сколько закрыто. Нулевой счётчик закрытых — норма,
   ненулевой при работающем вебхуке — повод проверить, почему вебхук опоздал.

Сверка также вызывается точечно, когда пользователь вернулся по `paid_<orderId>`, а заказ ещё
`pending`: бот делает ту же проверку по одному заказу, не дожидаясь пяти минут.

## 5. handleOrderPaid()

Единственное место, где заказ становится оплаченным. Зовётся из вебхука, из сверки и из точечной
проверки.

```ts
// src/lib/payments/handle-order-paid.ts (shape, not final code)
export async function handleOrderPaid(paymentId: string, payment: YooPayment): Promise<"granted" | "already"> {
  const result = await db.transaction(async (tx) => {
    const flipped = await tx.execute(sql`
      update orders
         set status = 'succeeded', paid_at = now(), raw_payload = ${payment}, updated_at = now()
       where payment_id = ${paymentId} and status = 'pending'
   returning id, user_id, course_id`);
    if (flipped.length === 0) return { status: "already" as const };  // lost the race or replay: do nothing
    const order = flipped[0];
    await grantEntitlement(tx, { ...order, source: "purchase" }); // insert, starts_at = now()
    await stopFunnels(tx, order.user_id, order.course_id, "purchased"); // funnels selling this course → stopped
    return { status: "granted" as const, orderId: order.id };
  });
  // After commit, never inside the transaction: pg-boss has its own connection pool (see 06 section 6).
  if (result.status === "granted") await enqueueAccessMessage(result.orderId); // boss.send, singletonKey = access:<orderId>
  return result.status;
}
```

Что важно:

- Выдача доступа и остановка прогрева этого курса идут в одной транзакции с переходом статуса. Либо
  всё, либо ничего.
- Сообщение «доступ открыт» ставится в очередь после коммита (`boss.send` с `singletonKey`), а уходит
  через `src/lib/telegram/send.ts`: сетевой вызов внутри транзакции держит соединение с базой, а
  очередь pg-boss живёт на своём пуле соединений и в транзакцию Drizzle не входит. Если процесс упал
  между коммитом и постановкой, сообщение теряется, но доступ уже выдан и виден в приложении и по
  возврату `paid_<orderId>`.
- `access_days` курса даёт `ends_at = now() + access_days`; `null` — бессрочный доступ (вопрос Q7
  в `PROJECT-STATE.md`).
- `UNIQUE entitlements_order_uq` — второй рубеж: даже если переход статуса когда-нибудь сломают,
  второй `INSERT` по тому же заказу упадёт.
- Ответ API (`payment`) сохраняется в `orders.raw_payload` для разбора споров.

### Промокоды

Проверка кода (существует, срок, `max_uses`, курс) и учёт использования идут в одной транзакции с
созданием заказа, на сервере. Для лимита `max_uses` считаются заказы `pending` и `succeeded` с этим
`promo_code_id`: отменённый заказ использование освобождает (для показа «сколько раз использован» в
`02-data-model.md` §5 считаются только `succeeded`). Проверка и вставка заказа делаются под блокировкой
строки `promo_codes` (`select ... for update`): два покупателя не получат последнее использование
одновременно. `orders.promo_code_id` хранит применённый код, цена считается из `courses.price_minor` и кода.

Заказ с нулевой суммой (`free_access` или скидка 100 %) в ЮKassa не идёт: платёж на 0 ₽ она не
примет. Такой заказ в той же транзакции становится `succeeded`, и дальше выполняется та же выдача
доступа, что в `handleOrderPaid` (`grantEntitlement`, `stopFunnels`, сообщение после коммита), только
с `source = 'promo'`, без запроса к API и с пустым `payment_id`. Код выдачи доступа остаётся один.
У такого заказа заполнен `promo_code_id`, а у его `entitlement` заполнен `order_id`, поэтому
использования промокода считаются по одному источнику, `orders` (формулы в `02-data-model.md` §5):
строки `entitlements` с `source='promo'` в счёт не добавляются, иначе бесплатный заказ посчитается дважды.

## 6. Возвраты

На старте возвраты делаются вручную в личном кабинете ЮKassa, кнопкой возврата у платежа. После этого:

1. Владелец в боте: `/revoke <tg_id> <course>` — ставит `entitlements.ends_at = now()` и пишет
   `admin_actions`.
2. Если известен заказ, бот спросит, отметить ли `orders.refunded_at` (по умолчанию да).
3. Статус заказа остаётся `succeeded`: деньги были получены, возврат — отдельное событие. Поэтому
   выручка равна полученному минус возвращённое (`02-data-model.md` §5). `refunded_at` означает полный возврат; частичный возврат в кабинете на старте в базе не
   учитывается, его сумму владелец сверяет по кабинету.

Автоматические возвраты по событию `refund.succeeded` — не на старте (уточнить по документации
состав события, если понадобится).

## 7. Тестовый и боевой магазин

| | Тестовый | Боевой |
|---|---|---|
| Ключи | `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` тестового магазина из кабинета | боевые |
| Деньги | не списываются, тестовые карты из документации | реальные |
| Вебхук | тот же URL, настраивается отдельно в кабинете тестового магазина | отдельная настройка |
| Где живёт | `.env.local` и стейдж, если он есть | `.env` на сервере |

Переключение — только заменой пары ключей в окружении. В коде ветвления «если тест» нет. Тестовые
карты и сценарии (успех, отказ банка, 3-D Secure) — в документации ЮKassa, раздел про тестирование.

## 8. Переменные окружения

```
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
YOOKASSA_RETURN_URL=https://t.me/<bot>?start=paid_      # prefix, orderId is appended
YOOKASSA_VAT_CODE=                                      # per the seller's tax regime
```

`return_url` строится только из `YOOKASSA_RETURN_URL` (префикс плюс `orders.id`), в коде платежей
`BOT_USERNAME` не используется. Имя бота в префиксе должно совпадать с `BOT_USERNAME` из
`infra/.env.example`: при смене бота меняются обе переменные.

Ключ `YOOKASSA_SECRET_KEY` на клиент не попадает, в логи не пишется. Заголовок `Authorization`
не логируется.

## 9. План проверки (до выката и после)

| Сценарий | Как проверить | Ожидаемо |
|---|---|---|
| Оплата, вебхук работает | тестовая карта | заказ `succeeded`, один `entitlement`, одно сообщение «доступ открыт» |
| Оплата, вебхук отключён | временно убрать URL в кабинете | оплата в первые минуты после создания заказа закрывается сверкой не позже чем через 10 минут, результат тот же |
| Дубликат вебхука | отправить тот же `payment.succeeded` дважды (`curl` с IP из диапазона в dev-режиме или прямой вызов `handleOrderPaid`) | второй вызов возвращает `already`, второго `entitlement` и второго сообщения нет |
| Гонка вебхук и сверка | тест: два параллельных вызова `handleOrderPaid` на один платёж | ровно один `granted`, один `entitlement` |
| Подделанный вебхук | `POST` с чужого IP; `POST` с нужного IP, но с `object.id` неоплаченного платежа | 403; статус заказа не меняется (платёж перечитан, он не `succeeded`) |
| Отмена оплаты | закрыть страницу оплаты, дождаться отмены или отказ карты | заказ `canceled`, доступа нет, повторная покупка возможна |
| Повторное «Купить» при живом платеже | открыть оплату, не платить, снова нажать «Купить» | тот же заказ, тот же `confirmation_url`, второго платежа нет |
