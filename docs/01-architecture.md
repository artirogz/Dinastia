# 01 — Архитектура

**Дата:** 2026-10-07. **Статус:** принята как основа для разработки. Изменения фиксируются в
`docs/11-decisions.md` и в `PROJECT-STATE.md`.

## 1. Что строим

Платформа платных видеокурсов внутри Telegram. Две поверхности, один бэкенд:

- **Бот** — вход для всех. Прогревы (цепочки сообщений по дням), продажа курса, оплата, выдача
  доступа, напоминания, кнопка «Открыть приложение». Админ-команды владельца.
- **Mini App** — для тех, кто купил. Список курсов, уроки с видео, конспект, материалы, задания,
  комментарии, прогресс.

Пять курсов на старте, десять через год. В курсе разделы, в разделе уроки. Урок: видео,
конспект, дополнительные материалы, задание, обсуждение.

## 2. Ограничения, которые определили архитектуру

| Ограничение | Следствие |
|---|---|
| Персональные данные остаются в России | Своя база и файлы на российском VPS. Никаких Supabase, Vercel, Cloudflare R2, Firebase, зарубежной аналитики |
| Один разработчик с Claude Code на подписке | Минимум движущихся частей: один язык (TypeScript), один фреймворк (Next.js), одна база (PostgreSQL), один образ Docker |
| Аудитория в России, Telegram замедляют | Приложение работает и внутри Telegram, и по обычной ссылке в браузере с входом через бота |
| Видео должно играть без YouTube | Видеохостинг с российской доставкой за абстракцией «провайдер видео», чтобы сменить без переписывания |
| Деньги | ЮKassa; оплата отмечается идемпотентно; вебхук дублируется фоновой сверкой |

## 3. Схема системы

```
                 ┌────────────────────────────────────────────────────────────┐
                 │  Российский VPS (Ubuntu 24.04, Docker Compose)              │
                 │                                                            │
 Telegram ──────►│  caddy (TLS, домен .ru)                                    │
 (бот, WebView)  │    ├── app.<домен>  ──► web   Next.js: экраны + API + вебхук бота
                 │    └── /api/tg/webhook ► web   (тот же процесс, grammY)      │
 Браузер ───────►│                                                            │
 (вне Telegram)  │  worker  Node: шаги прогревов, рассылки, сверка платежей,  │
                 │          синхронизация видео (pg-boss, очередь в Postgres)  │
                 │                                                            │
                 │  postgres 16   users, entitlements, courses, lessons,      │
                 │                orders, funnels, comments, progress …       │
                 │                                                            │
                 │  /data/media   материалы уроков (PDF, картинки), выдача по  │
                 │                подписанной ссылке через web                 │
                 └──────────┬──────────────────────┬──────────────────────────┘
                            │                      │
                     ЮKassa API (РФ)        Видеохостинг (Kinescope по умолчанию)
                     платежи, чеки,         видеофайлы без персональных данных,
                     вебхук + сверка        доступ к плееру через токен нашего бэкенда
```

Четыре контейнера: `caddy`, `web`, `worker`, `postgres`. `web` и `worker` собираются из одного
образа и одного репозитория; различаются командой запуска.

## 4. Почему один Next.js, а не отдельные фронт, API и бот

- Нет CORS, нет второго деплоя, нет расхождения типов между клиентом и сервером.
- Все ключи живут только на сервере. Клиент не знает ни токена бота, ни ключей ЮKassa, ни ключа
  видеохостинга.
- Бот через вебхук — это одна API-ручка. grammY даёт `webhookCallback(bot, "std/http")`, который
  встаёт в роут Next.js без адаптеров.
- Фоновая работа (прогревы по расписанию, сверка платежей) не умещается в запрос-ответ, поэтому
  вынесена в `worker`. Он импортирует тот же код бота, чтобы слать сообщения, и ту же схему базы.

Отдельный сервер на Fastify или NestJS здесь не нужен: нет второго клиента, нет команды, которая
делила бы фронт и бэк.

## 5. Стек

| Слой | Выбор | Зачем именно это |
|---|---|---|
| Приложение | Next.js (App Router), TypeScript strict, Tailwind | один проект на экраны и API; Claude Code знает его лучше всего |
| Telegram SDK | `@tma.js/sdk-react` (актуальное имя пакета сверить в context7 перед установкой) | типизированный доступ к `initData`, `expand()`, темам, кнопкам |
| Бот | grammY | лёгкий, типизированный, вебхук из коробки, conversations для сцен оплаты |
| База | PostgreSQL 16 в Docker + Drizzle ORM | миграции из схемы, SQL без магии, одна база на всё |
| Очередь | pg-boss | очередь и расписание прямо в Postgres, без Redis |
| Платежи | ЮKassa, официальный REST API | российский эквайринг, чеки 54-ФЗ |
| Видео | Kinescope (по умолчанию) за интерфейсом `VideoProvider`; запасной адаптер — своё HLS | подробно в `05-video-delivery.md` |
| Файлы | локальный том `/data/media` + подписанные ссылки | без S3 на старте; переезд на российский S3 (Selectel, Timeweb) по мере роста |
| Логи | pino → stdout → docker logs с ротацией | без зарубежного сервиса ошибок |
| Тесты | vitest (логика), Playwright (скриншоты и smoke) | |
| Прокси | Caddy | TLS сам, конфиг в десять строк |

Версии фиксируются при старте проекта: скилл `start-project` берёт текущие стабильные
(`npx create-next-app@latest`), а перед кодом против любой библиотеки Claude сверяется с
актуальной документацией (context7 или официальный сайт), а не с памятью.

## 6. Модули кода

```
src/lib/auth/        verifyInitData(), createSession(), readSession(), магические ссылки для браузера
src/lib/access.ts    requireCourseAccess(userId, courseId): есть ли право на курс (entitlements или admin)
src/lib/lessons.ts   getLessonForUser(userId, lessonId) — единственная дверь к контенту урока: внутри
                     requireCourseAccess() и проверка порядка разблокировки; возвращает playback,
                     конспект, материалы, задание, прогресс. Больше никто тело урока не читает
src/lib/video/       VideoProvider: интерфейс + адаптеры kinescope/ и hls/
src/lib/payments/    createPayment(), handleOrderPaid() (общий для вебхука и сверки), receipt 54-ФЗ
src/lib/funnels/     планирование шагов, стоп-условия (купил → цепочка останавливается)
src/lib/content/     импорт content/courses → база, рендер конспекта из блоков
src/bot/             grammY: /start, меню, покупка, «Открыть приложение», админ-команды
src/worker/          pg-boss: jobs funnel-step, broadcast, payments-reconcile, cleanup (список — 06-bot-and-funnels.md §6)
src/db/              schema.ts, миграции, клиент (пул Drizzle; у pg-boss в воркере свой пул, размеры — 06 §6)
src/app/             экраны: /courses, /courses/[slug], /lessons/[id], /profile; /admin (позже)
src/app/api/         auth/session, auth/magic, me, courses, lessons/[id], progress, comments,
                     assignments, video/authorize, payments/create, payments/webhook, tg/webhook,
                     dev/login (только dev)
```

Модули `src/lib/**`, которые импортирует `worker`, не импортируют `server-only`, `next/headers` и
прочее из `next/*`: воркер работает вне Next.js, и такой импорт уронит его на старте. Всё, что
зависит от запроса (cookie, заголовки), живёт в `src/app/**`.

## 7. Ключевые потоки

### 7.1 Вход из Telegram

1. Mini App открылась → клиент пробует `GET /api/me` с cookie.
2. 401 → клиент отправляет `initData` на `POST /api/auth/session`.
3. Сервер проверяет подпись HMAC-SHA256 по схеме Telegram, свежесть `auth_date` (5 минут) и
   одноразовость `hash`. Валидно → upsert `users`, выдача httpOnly-cookie
   (`SameSite=None; Secure`, подписанный JWT на 30 дней).
4. Все `/api/*` читают пользователя из cookie. Подробности и причины — `03-auth-and-security.md`.

### 7.2 Вход из браузера (вне Telegram)

Бот по команде `/web` (или кнопке «Открыть в браузере») присылает одноразовую ссылку
`https://app.<домен>/login?token=…` на 10 минут. Переход ставит ту же cookie. Дальше приложение
не отличает, откуда пришёл пользователь. Это страховка на случай замедления Telegram и путь для
десктопа.

### 7.3 Покупка

1. В боте: «Купить курс» → `createPayment()` создаёт `orders(pending)` и платёж ЮKassa с
   `confirmation_url` и чеком 54-ФЗ → бот отправляет кнопку оплаты.
2. Оплата → ЮKassa шлёт вебхук на `/api/payments/webhook`. Параллельно `worker` каждые
   5 минут сверяет с API ЮKassa `pending`-заказы, у которых подошёл `next_check_at` (очередь с
   растущим шагом, `04-payments-yookassa.md` §4).
3. Оба пути зовут `handleOrderPaid(paymentId, payment)`: атомарный `UPDATE orders SET status='succeeded'
   WHERE payment_id=$1 AND status='pending'`. Обновилась одна строка → выдать `entitlement`,
   остановить прогрев, отправить сообщение «доступ открыт» с кнопкой в приложение. Ноль строк →
   уже обработано, выйти молча.
4. Подробности, чеки, возвраты — `04-payments-yookassa.md`.

### 7.4 Просмотр урока

1. Экран `/lessons/[id]` (Server Component) и ручка `GET /api/lessons/[id]` зовут одну функцию
   `getLessonForUser(user.id, lessonId)` из `src/lib/lessons.ts`. Других путей к телу урока нет.
2. Внутри: `requireLessonAccess(user.id, lessonId)` — право на курс (`requireCourseAccess()`), урок
   опубликован, порядок пройден (при `courses.unlock_mode = 'sequential'` закрытый урок возвращает
   `locked` без контента). Нет доступа к курсу → 403 и предложение купить. Все проверки серверные:
   клиент только рисует замок.
3. Есть доступ → функция собирает `videoProvider.getPlayback({ videoRef, userId, lessonId })`
   (сигнатура в `05-video-delivery.md` §2; для Kinescope: id видео и короткоживущий токен авторизации,
   для HLS: подписанный URL манифеста), конспект блоками, материалы ссылками с download-token, задание,
   прогресс. Ручки `/api/video/authorize` (Kinescope) и `/api/media/[id]` (файлы) зовут ту же
   `requireLessonAccess()` с `lessonId` из своего токена, а не проверяют доступ по-своему.
4. Клиент сохраняет позицию просмотра каждые 10 секунд и при закрытии (`POST /api/progress`).
   90 % длительности → урок отмечен пройденным.

### 7.5 Прогрев

1. Владелец описывает цепочку в `content/funnels/<slug>.yaml`: шаги с задержкой (часы/дни), текст,
   медиа, кнопки. Импорт в базу скриптом.
2. `/start` с параметром (`?start=warmup-family`) или команда админа записывает пользователя в
   `funnel_enrollments`, `worker` ставит job на первый шаг.
3. Каждый шаг: проверить стоп-условия (купил, отписался, заблокировал бота) → отправить → поставить
   следующий. Ошибка 403 от Telegram («бот заблокирован») → пометить пользователя, цепочку
   остановить.
4. Рассылки по всем: батчами не быстрее 25 сообщений в секунду, с паузой по `retry_after` при 429.

### 7.6 Контент

На старте уроки и курсы живут файлами в `content/courses/<slug>/`: `course.yaml` (название, порядок
разделов, цена) и `lessons/NN-slug.md` (frontmatter: заголовок, раздел, id видео у провайдера,
материалы; тело: конспект в markdown с расширенными блоками). `npm run content:import`
загружает их в базу идемпотентно (по slug). Это дёшево для Claude и удобно владельцу: конспект
пишется в редакторе, видео загружается в кабинет видеохостинга, id вставляется в файл.

Админ-панель в приложении (`/admin`) — отдельный этап после запуска, когда станет понятно, какие
правки нужны чаще всего.

## 8. Инварианты (то, что должно быть невозможно нарушить)

1. **Контент урока выходит только через `getLessonForUser()`** (`src/lib/lessons.ts`), внутри которой
   стоит `requireLessonAccess()` (курс, публикация, порядок). Публичную программу курса для экрана
   `/courses/[slug]` отдаёт `getCourseOutline(userId, courseSlug)` из того же файла: названия модулей и
   уроков, длительность, состояние «пройден / доступен / закрыт / нужна покупка», без `body_md`,
   `video_ref`, материалов и заданий. Тест-сканер `tests/access-invariant.test.ts` проходит по всему
   `src/**` (страницы, server actions, API, бот, воркер) и падает, если вне `src/lib/lessons.ts` и
   импортёра контента `src/lib/content/` встречается чтение таблиц `lessons`, `lesson_materials`,
   `assignments` или вызов `getPlayback(`. Белый список файлов в тесте — закрытый, и каждая строка в
   нём с причиной. Второй тест запрашивает программу курса без доступа и проверяет, что в ответе нет
   полей контента. Проверка по роутам не годится: Server Component отдаёт данные без роута.
2. **Идентификатор пользователя — только из сессии.** Ручки не читают `tg_id`, `user_id` из тела
   или query. Тест-сканер на `req.json()`/`searchParams` с этими именами.
3. **Выдача доступа — только из `handleOrderPaid()` и из явной админ-команды.** Оба пишут строку в
   `entitlements` с `source` (`purchase` | `manual` | `promo`) и `granted_by`.
4. **Прогресс и статистика вычисляются, а не хранятся дважды.** «Пройдено 7 из 12» считается из
   `progress`, а не из поля-счётчика, которое разойдётся.
5. **Отправка сообщений пользователям идёт через один модуль `src/lib/telegram/send.ts`** с учётом
   лимитов и обработкой 403/429. Прямые `bot.api.sendMessage` в коде вне модуля — дефект.
6. **Каждый внешний получатель данных записан в реестре** (`03-auth-and-security.md` §8): Telegram,
   ЮKassa, видеохостинг (подписанный токен с внутренними id плюс IP и User-Agent зрителя), S3 для
   бэкапов. Новый внешний сервис, SDK или CDN без строки в реестре — дефект.
7. **Порядок разблокировки уроков решает сервер.** Режим курса хранится в `courses.unlock_mode`
   (`all` | `sequential`, вопрос Q8), и `getLessonForUser()` возвращает `locked` для закрытого урока. Клиент, который
   прячет кнопку, но получает контент по прямому запросу, инвариант нарушает.

## 9. Процессы и запуск

| Процесс | Команда | Что делает |
|---|---|---|
| `web` | `node server.js` (standalone-сборка Next.js) | экраны, API, вебхуки Telegram и ЮKassa; `GET /api/health` отвечает 200, если база доступна |
| `worker` | `node dist/worker/index.js` (сборка `npm run build:server`, esbuild-бандл четырёх входов: `src/worker/index.ts`, `src/db/migrate.ts`, `scripts/import-content.ts`, `scripts/admin.ts`) | pg-boss: прогревы, рассылки, сверка платежей; раз в 30 с обновляет файл `/tmp/worker-heartbeat` для healthcheck контейнера |
| миграции | `node dist/db/migrate.js` в init-контейнере перед стартом `web`; SQL-файлы лежат в `./drizzle` (`drizzle.config.ts` → `out: "./drizzle"`) | схема базы |
| импорт контента | `docker compose --env-file infra/.env -f infra/docker-compose.yml run --rm web node dist/scripts/import-content.js` | `content/courses` → база, идемпотентно |
| админ-CLI | `docker compose --env-file infra/.env -f infra/docker-compose.yml run --rm web node dist/scripts/admin.js <команда>` | те же операции, что админ-команды бота (`06` §4), без Telegram: `orders`, `find`, `grant`, `revoke`, `magic-link`, `forget`; сценарии — `12-operations.md` |

Оба служебных сигнала (`/api/health`, heartbeat) создаются на этапе M0: без них `infra/deploy.sh` не
пройдёт проверку живости, и это ожидаемо.

Деплой: один скрипт `infra/deploy.sh` на сервере: сборка образа из `git worktree` релизного коммита
(`HEAD` main или `--sha`) → миграции → `docker compose up -d` → `node scripts/smoke.mjs https://app.<домен>`;
при провале health или smoke сам поднимает последнюю хорошую версию из `infra/.release/current`.
Подробности — `09-infra-and-deploy.md` §6–§7.

## 10. Что сознательно не делаем на старте

- Отдельная админ-панель (контент файлами, модерация комментариев в боте).
- Мобильное приложение вне Telegram.
- Своя система рекомендаций, геймификация сверх прогресса и серии дней.
- Микросервисы, Redis, Kubernetes, CI/CD-пайплайны с матрицами. Один сервер, один compose.
- Подписки с рекуррентными списаниями (ЮKassa умеет, но это второй этап: нужна оферта и логика
  продления).

## 11. Масштаб

Расчёт на 10 курсов, до 5 000 пользователей, до 200 одновременных зрителей. Один VPS с
2 vCPU / 4 ГБ / 40–60 ГБ NVMe — стартовая гипотеза с запасом (расчёт в `09-infra-and-deploy.md` §1):
видео раздаёт видеохостинг, а не сервер; 200 одновременных зрителей, сохраняющих позицию каждые 10 секунд,
дают около 20 записей в секунду, что для Postgres на NVMe не нагрузка; остальной трафик приложения меньше.
Запас проверяется замером на M7: сборка образа при работающем приложении и записи прогресса.
Узкое место при росте — рассылки (лимиты Telegram), не база.
