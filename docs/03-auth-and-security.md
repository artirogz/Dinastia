# 03 — Вход, сессии, права, персональные данные

Это поверхность класса «деньги и доступ»: любая правка здесь проходит отдельное ревью
(`dev-flow-lite`, уровень R2), даже если изменилась одна строка.

## 1. Вход через Telegram (Mini App)

Telegram передаёт в Mini App строку `initData`: поля пользователя, `auth_date`, `hash`. Проверка на
сервере, по официальной схеме:

```
secret_key = HMAC_SHA256(key = "WebAppData", data = <bot_token>)
data_check_string = поля initData без hash, отсортированные по ключу, через "\n" в виде key=value
ok = hex(HMAC_SHA256(key = secret_key, data = data_check_string)) == hash
```

Дополнительно к подписи сервер требует:

1. **Свежесть.** `now - auth_date ≤ 300 с` (`SESSION_INIT_DATA_TTL_SEC`). Старую подпись можно
   украсть и предъявить позже.
2. **Одноразовость без обрыва живого пользователя.** Клиент при запуске сначала пробует уже
   выданную cookie (`GET /api/me`) и предъявляет `initData` только при 401, поэтому перезагрузка
   экрана подпись не тратит. На сервере первая вставка `hash` в таблицу `init_data_uses` — атомарная
   заявка (`INSERT … ON CONFLICT DO NOTHING RETURNING`). Повтор того же `hash` принимается вместе с
   cookie того же пользователя, а без cookie — только в первые 60 секунд после первого использования
   (ответ с cookie мог не дойти до клиента): в этом окне выдаётся та же сессия (`init_data_uses.session_jti`),
   после него 401, и клиент просит открыть приложение заново (Telegram выдаст свежий `initData`).
   Повторы считаются (`use_count`): всплеск по одной подписи виден как сигнал перехвата.
3. **Проверка только на сервере.** Токен бота в клиент не попадает, значит и проверить там нечего.

Успех → `users` upsert по `tg_id` (имя, username, фото, язык) → cookie. Без `consent_at` приложение
показывает экран согласия (тот же текст, что в боте, `06-bot-and-funnels.md` §2) и до нажатия «Принимаю»
ничего больше не отдаёт; на каком основании хранятся данные, которые Telegram передаёт при открытии до
согласия, решает владелец с юристом (вопрос Q11).

## 2. Сессия

- httpOnly-cookie с подписанным JWT (HS256, секрет `SESSION_SECRET`), срок 30 дней, продлевается при
  активности.
- **`SameSite=None; Secure` всегда, когда запрос пришёл по HTTPS.** Telegram показывает Mini App во
  фрейме; cookie с `SameSite=Lax` браузер выбрасывает, и вход выглядит как «приложение не
  кликается»: сессия выдана, следующий запрос уже 401. Признак прода выбирается по протоколу
  запроса (`x-forwarded-proto`), а не по `NODE_ENV`: режим сборки не знает, что снаружи туннель.
- Все ручки `/api/*` читают пользователя из cookie через `readSession()`. Идентификаторы из тела
  или query не принимаются.
- Защита от CSRF для изменяющих ручек: проверка `Origin`/`Sec-Fetch-Site` на свой домен
  (`guardSameOrigin()`), потому что cookie с `SameSite=None` отправляется с любого сайта.
  Исключений три, и все без cookie: `/api/tg/webhook` (секретный заголовок), `/api/payments/webhook`
  (подпись и IP) и `/api/video/authorize` (его зовёт сервер видеохостинга, не браузер: проверяются подпись
  нашего токена `KINESCOPE_AUTH_SECRET`, срок 10 минут и совпадение id видео с уроком из токена,
  `05-video-delivery.md` §3). Новое исключение = запись в этом разделе.
- Если браузер не принял cookie (приватный режим, запрет сторонних cookie в WebView), клиент
  получает 401 на первом же запросе после входа. Запасной путь: `POST /api/auth/session` отдаёт
  тот же JWT в теле ответа, клиент держит его в памяти страницы (не в `localStorage`) и шлёт
  заголовком `Authorization: Bearer`; `readSession()` принимает оба источника. Заголовок несут только
  fetch-запросы клиента: навигация и Server Components его не передают, а после перезагрузки страницы
  токен исчезает и вход повторяется, поэтому это запасной режим для API, а не замена cookie. Включать только
  после того, как проблема воспроизведена на устройстве, не заранее.

## 3. Вход из браузера без Telegram

Нужен на случай замедления Telegram в России и для десктопа.

1. Бот по команде `/web` генерирует токен (32 случайных байта), сохраняет `magic_links(token_hash =
   sha256(token), user_id, expires_at = now + 10 мин, used_at)` и присылает ссылку
   `https://app.<домен>/login?token=…` с выключенным предпросмотром (`link_preview_options:
   { is_disabled: true }`). Сам токен в базе не хранится.
2. `GET /login?token=…` ничего не тратит: показывает страницу «Войти как <имя>» с кнопкой. Иначе
   ссылку сожжёт первый же бот предпросмотра или антивирус, который откроет её раньше человека.
3. Кнопка делает `POST /api/auth/magic` с токеном в теле: строка ищется по `token_hash` с
   `used_at IS NULL AND expires_at > now()`, атомарно помечается использованной (`UPDATE … RETURNING`),
   выдаётся та же cookie, редирект на `/courses`. Повторный POST → 410 и подсказка попросить
   новую ссылку у бота.
4. Токен в логах не печатается; `cleanup` раз в час удаляет просроченные строки.

Альтернатива для будущего: Telegram Login Widget. Не берём на старте, потому что виджет грузит
скрипт с домена Telegram, который может быть замедлен, а ссылка из бота работает всегда, пока
работает сам бот.

## 4. Вход для разработки

`POST /api/dev/login` сам подписывает `initData` тем же алгоритмом, что Telegram, и прогоняет через
ту же проверку. Подмена источника строки, а не проверки подписи. Ручка существует только при
двух условиях сразу: `NODE_ENV !== "production"` и `DEV_LOGIN=1`. В проде её нет по построению.
Так экраны прокликиваются и снимаются Playwright без телефона.

`/api/dev/login` при вызове создаёт (или находит) пользователя «Dev» с `tg_id = 1` и выдаёт ему
`entitlement` на `example-course` (`source='manual'`, `granted_by` null): так `scripts/visual-check.mjs`
снимает экраны урока детерминированно. Запрос без заголовка `Origin` своего домена отклоняется так же,
как любая изменяющая ручка; скрипт его присылает.

## 5. Права

| Роль | Как определяется | Что может |
|---|---|---|
| Пользователь | любая проверенная сессия | свои курсы, прогресс, комментарии |
| Купивший курс | строка в `entitlements` с активным сроком | контент этого курса |
| Админ | `users.role = 'admin'`, назначается только через `ADMIN_TG_IDS` в `.env` при старте | команды бота: выдать доступ, запустить рассылку, удалить комментарий, статистика |

Право на курс проверяет одна функция `requireCourseAccess(userId, courseId)`: `entitlements` с
`starts_at ≤ now < coalesce(ends_at, 'infinity')` или `role = 'admin'`. Право на конкретный урок —
`requireLessonAccess(userId, lessonId)` в том же `src/lib/lessons.ts`: курс через `requireCourseAccess()`,
урок опубликован, порядок разблокировки (`courses.unlock_mode`) пройден. Контент урока выходит только
через `getLessonForUser(userId, lessonId)`, которая её зовёт; `/api/video/authorize` и `/api/media/[id]`
зовут её же с `lessonId` из токена. Публичную программу курса без контента отдаёт `getCourseOutline()`
(`01-architecture.md` §8). Тест-сканер по `src/**` описан там же.

## 6. Вебхуки

- `/api/tg/webhook` принимает апдейты только с заголовком `X-Telegram-Bot-Api-Secret-Token`,
  равным `TG_WEBHOOK_SECRET`. Иначе 401 без тела.
- `/api/payments/webhook` проверяет, что IP отправителя входит в опубликованные диапазоны ЮKassa, и
  **никогда не верит телу**: по `object.id` перечитывает платёж через API ЮKassa и только затем зовёт
  `handleOrderPaid()`. Подробности — `04-payments-yookassa.md`.

## 7. Комментарии (пользовательский контент)

- Текст экранируется при выводе, HTML от пользователя не рендерится.
- Лимиты: не чаще одного комментария в 10 секунд на пользователя, не длиннее 2 000 символов.
  Лимит считается по пользователю, и блокировка берётся по тому же ключу (иначе гонка двух
  параллельных запросов обходит лимит).
- Жалоба — запись в `comment_reports`, админу уходит карточка в бот. Удаление помечает
  `deleted_at`, текст остаётся в базе для разбора.
- Комментарий резолвится вместе с проверкой доступа к уроку: перебор `id` не должен раскрывать
  существование скрытого урока.

## 8. Персональные данные и 152-ФЗ

Что мы храним о человеке: `tg_id`, имя, username, фото (ссылка), язык, покупки, прогресс,
комментарии, email или телефон для чека 54-ФЗ. Всё это персональные данные граждан РФ.

**Техническая часть (закрывает разработка):**

| Требование | Как выполнено |
|---|---|
| Хранение в РФ (ст. 18 ч. 5) | Postgres, файлы, логи, бэкапы — на российском VPS и в российском S3 |
| Каждый внешний получатель данных известен | реестр получателей ниже; иностранных получателей нет, видеохостинг выбирается с российским юрлицом и хранением в РФ |
| Нет зарубежной аналитики и трекеров | Google Analytics, Яндекс.Метрика в WebView, Sentry.io, Vercel Analytics не ставятся. Нужна статистика → self-hosted Umami или свои события в базе |
| Логи без лишнего | в логи не пишутся `initData`, токены, тексты сообщений пользователей |
| Удаление по запросу | команда админа `/forget <tg_id>`, алгоритм ниже |
| Минимизация | email/телефон для чека запрашиваются при покупке и хранятся в `orders`, не в профиле |

**Реестр получателей данных** (новый внешний сервис = новая строка здесь и в политике владельца):

| Получатель | Что уходит | Зачем |
|---|---|---|
| Telegram | `tg_id`, имя, тексты сообщений бота | сам канал общения и источник данных |
| ЮKassa (РФ) | сумма, номер заказа, email или телефон для чека | оплата и чек 54-ФЗ |
| Видеохостинг (Kinescope; юрлицо и регион хранения подтвердить при договоре, Q5) | наш подписанный токен с внутренними id пользователя и урока (читаются без ключа; имени и `tg_id` в нём нет), IP и User-Agent зрителя, как у любого веб-сервера | авторизация просмотра |
| S3 российского провайдера | полный дамп базы и файлы, зашифрованные до выгрузки (Q9) | резервные копии |

**Алгоритм `/forget <tg_id>`** (одна транзакция, идемпотентен):

1. `users`: `first_name`, `last_name`, `username`, `photo_url` → null; `consent_at`, `marketing_consent_at` → null;
   `anonymized_at` = now. `readSession()` отвергает сессию пользователя с `anonymized_at`, так что действующие
   cookie и Bearer-токены перестают работать без списка отзыва.
2. `comments` пользователя: `deleted_at` = now, `body` → '' (дерево ответов сохраняет структуру).
3. `assignment_submissions` пользователя удаляются строками вместе с файлами под `MEDIA_ROOT` (не обнуляются:
   `CHECK(body IS NOT NULL OR file_key IS NOT NULL)` этого не позволит); `progress` удаляется.
4. `magic_links` и `init_data_uses` пользователя удаляются; `funnel_enrollments` → `stopped`,
   `stop_reason='forgotten'`; рассылки его не включают (обезличенные исключены по `anonymized_at`).
5. `orders` остаются (суммы, даты, `payment_id` нужны бухгалтерии), но `receipt_contact` и `raw_payload` → null.
6. Новый `/start` того же `tg_id` после этого — обычный upsert: имя заполняется заново, `anonymized_at`
   сбрасывается, согласие спрашивается снова.

Сроки хранения по категориям (заказы, логи, бэкапы) владелец фиксирует в политике; по умолчанию логи
7 дней (`09-infra-and-deploy.md` §9), бэкапы 14 дней, заказы — срок, который требует бухгалтерия.

**Организационная часть (закрывает владелец как оператор, не разработчик):**

- Политика обработки персональных данных на сайте/в боте, ссылка при первом входе и перед оплатой.
- Публичная оферта на курсы (ЮKassa и 54-ФЗ её требуют).
- Согласие на обработку ПД и ознакомление с офертой: кнопка «Принимаю» при первом `/start`, факт, время
  и версия текста пишутся в `users.consent_at` и `consent_version`. Согласие на рекламные сообщения
  (анонсы, рассылки) — отдельная кнопка и отдельное поле `marketing_consent_at`, отзыв командой `/stop`
  (`06-bot-and-funnels.md` §2–3). Тексты всех трёх документов готовит владелец (вопрос Q11).
- Уведомление Роскомнадзора о начале обработки ПД (подаёт оператор; форма на сайте РКН).
- В политике видеохостинг указывается как получатель технических данных (IP, User-Agent, подписанный
  токен с внутренними идентификаторами). Иностранный получатель означал бы трансграничную передачу с
  отдельным уведомлением РКН (ст. 12 152-ФЗ), поэтому хостинг выбирается с российским юрлицом и хранением
  в РФ; это проверяется при заключении договора (Q5).

Это список, а не юридическая консультация: формулировки политики и оферты проверяет юрист владельца.

## 9. Секреты и окружение

```
BOT_TOKEN, TG_WEBHOOK_SECRET, ADMIN_TG_IDS
SESSION_SECRET (≥ 32 байта), SESSION_INIT_DATA_TTL_SEC=300
DATABASE_URL
YOOKASSA_SHOP_ID, YOOKASSA_SECRET_KEY, YOOKASSA_RETURN_URL
VIDEO_PROVIDER=kinescope|hls, KINESCOPE_API_KEY, KINESCOPE_PROJECT_ID, KINESCOPE_AUTH_SECRET, HLS_SIGNING_SECRET
MEDIA_ROOT=/data/media, MEDIA_SIGNING_SECRET
PUBLIC_APP_URL=https://app.<домен>
DEV_LOGIN=0
```

Полный перечень с переменными сервера (домен, Postgres, бэкапы, ссылки на политику и оферту) —
`infra/.env.example`. Секреты только в `.env` на сервере и в `.env.local` у разработчика. В репозитории лежит
`infra/.env.example` без значений. Проверка наличия обязательных переменных при старте процесса,
с понятной ошибкой, а не падением в середине запроса.

## 10. Чек-лист перед выкатом поверхности доступа

Метка в скобках — этап, на котором пункт закрывается (`08-roadmap.md`); ревью R2 этапа проверяет только
свои пункты.

- [ ] (M2) Подпись `initData` проверяется тестом на эталонном примере и на подделанном.
- [ ] (M2) Повтор `hash` без cookie позже 60 с → 401; в окне 60 с → та же сессия; с cookie того же пользователя → 200.
- [ ] (M2) Cookie на HTTPS имеет `SameSite=None; Secure; HttpOnly`.
- [ ] (M2) Чужой `tg_id` в теле запроса игнорируется (тест).
- [ ] (M2) Урок без `entitlement` → 403; закрытый по порядку урок → `locked` без контента.
- [ ] (M2) Magic-ссылка не сгорает от предпросмотра: `GET /login?token=` не меняет `used_at`.
- [ ] (M3) Файл материала без действующего download-token или с поддельным → 403; `/api/video/authorize`
      с токеном другого урока → 403. Ссылка с живым токеном открывается у любого до истечения 10 минут —
      признанный риск, записан здесь.
- [ ] (M4) Вебхук Telegram без секрета → 401.
- [ ] (M6) `/forget` выполняет алгоритм §8 целиком: профиль обезличен, комментарии и ответы с файлами
      удалены, cookie пользователя перестаёт работать, заказы остались без контакта.
- [ ] (M7) Ручка `/api/dev/login` отсутствует в прод-сборке (`curl` → 404).
